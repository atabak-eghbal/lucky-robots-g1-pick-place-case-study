The Challenge

The goal was simple to describe and hard to implement: move a red cylinder from a source table to a target table using the Unitree G1 humanoid in MuJoCo. The original repository shipped with manual keyboard control, walker and reacher ONNX policies, the robot model, a predefined scene, and multi-camera observability. The case study was about turning that demo into an autonomous baseline without losing clarity on what was failing.

Why This Is Hard

  • Humanoid locomotion and manipulation must be coordinated, not staged.
  • The reacher policy consumes pelvis-frame targets, not world-frame goals.
  • Grasping is contact-rich and highly sensitive to fingertip pose.
  • Learned policies behave empirically and can drift outside expected regimes.
  • Perception and manipulation timing determine whether the grasp is stable.

System Decomposition

A modular stack allowed each subsystem to be debugged in isolation while still supporting an end-to-end task. The pipeline is split into perception, locomotion, manipulation, grasping, and sequencing.

Perception

Depth + segmentation back-projection to recover object pose.

Locomotion

ONNX walker policy drives coarse navigation and stance control.

Manipulation

ONNX right reacher overlays arm motion on top of gait.

Grasp

Kinematic attachment backend for deterministic pickup and release.

Sequencing

Finite-state machine coordinates all modules and timeouts.

Architecture

The baseline connects policy logic to MuJoCo through a small set of focused modules that encapsulate control and perception:

  • run.py as the runtime orchestrator.
  • common/controller.py as the walker/reacher controller.
  • common/grasp.py as the grasp backend.
  • policies/fsm_core.py as the FSM logic.
  • policies/fsm_visual_oracle.py as the visual extension.
  • vision/geometry.py and observer.py as the perception layer.

FSM Baseline

The first autonomous version used an explicit finite-state machine so that each phase of the task could be inspected and tuned without conflating locomotion, perception, and grasping issues.

FSMs were chosen over end-to-end RL for the initial baseline because they are easier to debug, easier to test, better for isolating locomotion vs. manipulation failures, and more reliable when time is limited.

Visual Oracle

A ground-truth lookup was used first to debug behavior quickly. The Visual Oracle then replaced source-side object lookup by estimating the cylinder pose from camera depth and segmentation. The estimate is EMA-smoothed and frozen during descent and close-grip phases to avoid last-moment jitter.

Key Engineering Lessons

The Normalization Trap

Mixing raw MuJoCo coordinates with normalized policy inputs can silently poison reacher targets. A single canonical frame prevented hidden offsets.

The Always-On Reacher

Leaving the reacher engaged across walking phases caused drift. Gating the reacher by FSM state stabilized navigation.

The Reacher Accuracy Floor

Even with perfect targets, the reacher has a minimum error bound. The grasp logic needed to tolerate that floor.

The Asymptotic Turn-Rate Problem

The walker can slow as it nears alignment, stretching approach time. Explicit timeouts ensured state transitions still progressed.

Why Timeouts Were Necessary

Perception glitches and contact noise made some phases non-terminating. Timeouts bounded retries and simplified debugging.

Limitations

  • Kinematic grasping is a shortcut that hides contact dynamics.
  • The Visual Oracle is not a learned detector.
  • Target-side robustness still needs improvement.
  • On-table checks need post-settle evaluation.
  • The wrist camera is not fully exploited yet.
  • Sim-to-real transfer will require additional work.

Next Steps

  • Introduce a learned detector such as YOLO for object localization.
  • Apply domain randomization to improve robustness.
  • Add contact-aware grasping and slip detection.
  • Refine target navigation for tighter placement accuracy.
  • Include post-DONE settling checks to validate success.
  • Build a richer robustness dashboard for debugging.
  • Integrate a demo video alongside the case study.

Closing

The result is not a final production robot policy, but a strong modular autonomous baseline that demonstrates decomposition, debugging, and iteration.
