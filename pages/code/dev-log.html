Modular skeleton

DEV_LOG records the extraction of run.py, controller logic, and the FSM into separate modules so that each piece could be debugged and tested independently. The refactor produced a known-good baseline before any autonomous logic was layered on top.

Smoke test evidence

The log records the first passing run of scripts/smoke_env.py, which asserts that the environment, cameras, bodies, sites, joints, and both ONNX policies all load cleanly. This established a known-good baseline before any rollout. Status: ✓ Verified

Normalization trap

The normalization issue proved the ONNX models already normalize internally. The diagnosis was made by logging policy output magnitudes under two input conditions: 

raw zeros        → action max = 0.628
normalized zeros → action max = 14.78

The 23× difference confirms double-normalization. Conclusion: raw, un-normalized observations must be passed to the walker ONNX policy. Status: ✓ Verified

Always-on reacher

DEV_LOG notes that the right reacher must run at every control tick, even when reach_active is false. The walker ONNX policy observes arm joint positions; allowing those joints to drift outside the carry pose introduces out-of-distribution observations and degrades gait stability. Gating the reacher off during locomotion-only phases produced observable gait degradation, which is how this constraint was discovered.

Reacher accuracy floor

The reacher plateaued at approximately 0.12–0.13 m residual radial error and could not converge further through continued inference. This floor was measured during development by logging palm-to-target distance over time and observing the asymptote.

This observation shaped three downstream design choices:

  • Hover and grasp-height thresholds were set to be reachable within the floor, not at the geometric cylinder center.
  • The kinematic attach window was calibrated to trigger within the floor band.
  • Timeout fallbacks were added for DESCEND_SOURCE because the policy may stall near the floor without triggering a threshold.

Status: ✓ Verified (logged)

Kinematic grasp evidence

The attachment snap distance was calibrated to the reacher accuracy floor. The grasp backend logs the palm-to-cylinder distance at the moment attachment triggers. The reference run recorded: 

Attach: dist = 0.128 m
snap_offset = 0.030 m

The attach distance of 0.128 m falls within the ~0.12–0.13 m floor band, confirming the threshold was set to match the practical policy limit, not an idealized geometry. Status: ✓ Verified (logged)

Caveat: kinematic attachment is a simulation shortcut. It bypasses contact dynamics and finger forces and should not be treated as evidence of physical grasp quality.

Target-side false positive — full bug timeline

v1: single-condition check (incorrect)

The initial implementation of _approach_target() in fsm_core.py used a single condition to gate the transition from APPROACH_TARGET to HOVER_TARGET: whether the palm was within a configured reach-window distance of the target drop point.

This produced false positives. During target-side navigation, the robot's forward arm extent could bring the palm within the reach window while the pelvis was still several steps away from the target table. The FSM would advance to HOVER_TARGET, then immediately fail to maintain the hover position because the whole-body posture was not yet aligned.

Root cause

A reach-window check is palm-relative. It measures whether the palm is close to a world point, but does not verify that the robot's base is within stable operating range of that point. With a forward-biased arm carry pose, the palm leads the pelvis by a significant lateral distance, making the check insufficient on its own.

v2: compound guard (fix)

The fix replaced the single condition with a compound guard. All three conditions must hold before the FSM transitions: 

TARGET_STAND_DIST = 0.24        # body proximity (metres)
PHASE1_ALIGN_TOL  = 0.40        # yaw alignment (radians)
TARGET_APPROACH_DIST_THRESH = 0.08  # reach window (metres)

The additional body-proximity check (0.24 m) ensures the pelvis is near the target stand before the transition is allowed. The yaw-alignment check (0.40 rad) prevents transitions while the robot is still rotating, which also contributed to the false positive given the asymptotic turn-rate slowdown documented separately.

These values were chosen empirically for this scene geometry. They are not guaranteed to generalize to different table layouts or robot starting positions. Status: ✓ Verified (dev log)

Visual-pass nuance

Several behaviors in the baseline are listed as ◎ Visually verified rather than ✓ Verified. The distinction matters.

What a visual pass means

A visual pass is an observation made during a single rendered MuJoCo reference run. A human watched the run, saw the described behavior occur, and recorded it. This is useful for confirming that a code path executes and produces plausible motion. It is not a programmatic assertion.

What a visual pass does not prove

  • It does not prove reproducibility across varied initial conditions.
  • It does not confirm terminal state. In particular, the placement success (cylinder on the target table) was judged by watching the render — no post-DONE proximity check was executed to confirm the cylinder's final position programmatically.
  • It does not establish success rate. One observation is a sample of one.

Upgrade path

Any visually-verified claim can be upgraded to verified by adding a headless assertion that checks the same condition without a rendered display. For placement, this means a post-DONE ground-truth proximity check that confirms the cylinder rests within a tolerance of the target surface center.

Until that check exists, placement success should be reported as a single visual observation, not as a confirmed outcome.
