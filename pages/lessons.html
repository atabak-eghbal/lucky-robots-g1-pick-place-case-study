These lessons capture the key decisions and failure modes that emerged while converting the manual demo into a modular baseline. Each entry is grounded in a specific logged observation or design decision; none is a post-hoc rationalization.

Engineering lessons

Failure Mode

The Normalization Trap

The walker ONNX policy already applies internal normalization. Adding external normalization double-normalized observations, destabilized the gait, and caused hard-to-trace drift. This was diagnosed by comparing policy outputs: raw-zero input produced a maximum action of 0.628; normalized-zero input produced a maximum action of 14.78 — confirming the models expect raw observations.

Design Decision

The Always-On Reacher

The walker observes arm joint positions, so the right reacher had to run unconditionally at every tick, even during locomotion-only phases. Keeping the arm in a known carry pose prevented out-of-distribution walking behavior. Gating the reacher off during approach caused observable gait degradation.

Limitation

The Reacher Accuracy Floor

The right reacher has a practical accuracy floor of approximately 0.12–0.13 m radial error that the policy cannot overcome through continued inference alone. Hover and grasp thresholds, and the kinematic attach window, were all tuned around this floor rather than assuming the policy would converge to a geometrically precise pose. The observed attach distance of 0.128 m (development log) sits within this band.

Evidence

The Asymptotic Turn-Rate Problem

Target-side navigation required empirical tuning because the walker's effective angular response slows asymptotically as it approaches the desired heading. This contributed to the target-side false positive (see below): the robot could partially satisfy a reach window while still rotating, which is why yaw alignment was added as an explicit guard condition (PHASE1_ALIGN_TOL = 0.40 rad).

Validation Bug

Target-Side False Positive — Bug Timeline

v1 (before fix): The transition from APPROACH_TARGET to HOVER_TARGET checked only whether the palm was within a reach-window distance. This was insufficient: the reach window could be satisfied while the robot's pelvis was still mid-transit toward the target table, causing the FSM to advance prematurely.

Root cause: A distance check on the reach window (palm-relative) does not capture whole-body position. The pelvis can be far from the target table while the arm's forward extent puts the palm within a loose reach distance.

Fix (v2): A compound guard replaced the single condition. All three must hold simultaneously before the transition is allowed:

  • palm within reach window
  • body within 0.24 m of target stand (TARGET_STAND_DIST)
  • yaw error ≤ 0.40 rad (PHASE1_ALIGN_TOL)

The fix is visible in fsm_core.py's target navigation phase and documented in the dev log. The values 0.24 m and 0.40 rad were chosen empirically for this scene geometry.

Key Insight

The Visual Oracle Freeze

The vision estimate is designed to be frozen during DESCEND_SOURCE and CLOSE_GRIP to avoid self-occlusion jitter as the arm lowers over the cylinder. Updating the EMA target during descent would shift the reacher goal mid-approach, causing instability. Freezing accepts a static target for the last few centimetres in exchange for deterministic, jitter-free behaviour through grip closure.

The visual-pass nuance

Several behaviors listed in the results page carry a ◎ Visually verified label. It is worth being precise about what that label means.

A visual pass means: during development, a single reference MuJoCo run was rendered and watched. The described behavior was observed in that run. This is useful for confirming that code paths execute and produce plausible motion, but it has clear limits:

  • It was one run with one set of initial conditions, not a statistical sample.
  • Post-DONE table placement was not confirmed by a programmatic check — the cylinder appeared to rest on the table, but sensor-free visual inspection of a single frame is not a reliable proxy for a proximity assertion.
  • Visually passing behaviors can fail under small perturbations to initial conditions, contact timing, or floating-point non-determinism across platforms.

The distinction between headless-validated and visually-verified claims is maintained throughout the results page precisely because these two evidence levels support different engineering conclusions. A headless-validated result can be re-run and re-checked automatically. A visually-verified result needs programmatic confirmation before it can be relied upon.
