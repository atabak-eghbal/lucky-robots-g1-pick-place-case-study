Step 15 Diagnostic Finding

The harness infrastructure worked: it loaded all 554 steps, produced finite metrics, preserved grip timing with zero mismatches, and wrote artifacts. However, arm-only replay produced a mean palm error of 0.263667 m and ever_attached=False. The robot never picked up the cylinder.

Root cause: The 7D palm-delta action representation captures arm end-effector motion but omits the locomotion commands that carry the robot's base toward the object. Without the walker's position as context, the replayed palm deltas accumulate error relative to the floating base and cannot reproduce the full pick-and-place task.

This is strong engineering evidence. A working harness with a negative arm-only result precisely identifies what was added in Step 16: locomotion context or teacher commands.

What this confirms — and what it does not

  • The replay harness infrastructure is validated end-to-end.
  • Grip timing is preserved: zero mismatches across 554 steps.
  • Palm error metrics and plots are finite and reproducible.
  • OpenVLA is not implemented. No model loaded, no GPU used.
  • Arm-only 7D replay is not sufficient for the floating-base humanoid task.
  • Step 16 (hybrid replay / schema upgrade) has been validated.

Step 16 — Hybrid Replay / Schema Upgrade  Validated

Step 16 upgraded the VLA demonstration schema to include locomotion and reach-command context. It then compared sparse replay, every-tick teacher-command replay, and hybrid-7D replay to determine whether the future VLA action target should be raw 7D palm deltas or the G1-native command interface.

Schema upgrade

The demo record now stores the FSM teacher command fields in addition to the 7D action:

walk_cmd
reach_target_pelvis
reach_active
grip_closed
action_7d

Replay modes tested

  • arm-only: 7D palm deltas + grip, no locomotion.
  • teacher-command: recorded FSM-native commands.
  • hybrid-7d: recorded walk command + 7D adapter for manipulation.

Critical finding

Every-tick teacher-command replay reproduced the teacher exactly. Hybrid-7D still failed. This means the replay pipeline is faithful, but relative palm deltas are not the right first learned action target for this G1 stack.

First result — sparse command replay exposed a timing issue

The first upgraded dataset used record-every=5. It successfully recorded the new command fields, but replay fidelity was poor, even in teacher-command mode.

Sparse recording compressed the command stream. The replay script applied each recorded row as if it represented one control tick, but the original data represented every fifth control tick. This showed that command replay must preserve control-rate timing.

Step 19 — Dataset Filtering / Sample Weighting / Training Views  Validated

Step 19 builds safer derived training views from the G1-native dataset. It keeps the original dataset unchanged, reduces idle-heavy records in a filtered view, preserves rare grip-transition phases, and writes normalized per-sample weights.

Why Step 19 exists

Step 18 showed that the exported dataset is structurally valid, but still imbalanced: APPROACH_TARGET dominates, CLOSE_GRIP and OPEN_GRIP are extremely rare, and the beginning of the rollout contains idle-heavy records. Step 19 creates safer dataset views before any model inference or fine-tuning.

Main conclusion:

Step 19 passed. The pipeline can now create full, filtered, and weighted views while preserving rare transition records. The data is better prepared for debugging baselines, but it is still a single-trajectory dataset and should not be used for robust generalization claims.

Why This Page Exists

The current submission solves the task with a ground-truth FSM baseline and documents a Visual Oracle perception extension. The next research question is whether a generalist Vision-Language-Action model such as OpenVLA can be adapted to this G1 humanoid task.

However, OpenVLA should not be plugged directly into the G1 controller, because the action spaces and embodiments differ significantly. This page documents the reasoning, staged plan, and decision log for doing this carefully.

Core Goal

Goal: Investigate whether a VLA model can map G1 camera observations and a language instruction into useful manipulation actions for the red-cylinder pick-and-place task.

Language instruction example:
"Pick up the red cylinder and place it on the blue table."

Main Engineering Constraint

OpenVLA predicts a 7-DoF robot action for supported robot embodiments:

[dx, dy, dz, droll, dpitch, dyaw, gripper]

The G1 stack consumes:

  • walk_cmd
  • reach_target in pelvis frame
  • reach_active
  • grip_closed

Therefore, the first engineering challenge is not model loading. It is defining an adapter between OpenVLA-style actions and the G1 walker / reacher / grip stack.

Recommended Architecture

Vision / Language Input
        ↓
OpenVLA or VLA model
        ↓
7D end-effector action proposal
        ↓
G1VLAActionAdapter
        ↓
existing walker + right_reacher + grip backend
        ↓
MuJoCo G1 task execution
  • The walker should remain classical at first.
  • The right_reacher ONNX should remain the arm controller at first.
  • OpenVLA should first propose manipulation deltas or waypoints, not full-body humanoid joint targets.

Why We Should Not Replace the Whole Controller First

Embodiment mismatch

OpenVLA was not trained specifically on this G1 MuJoCo humanoid setup.

Action-space mismatch

The G1 stack uses pelvis-frame reach targets and a walker/reacher abstraction, not direct OpenVLA actions.

Infrastructure cost

OpenVLA inference/fine-tuning needs GPU/cloud resources, while adapter and replay tests can run locally.

Debuggability

The FSM baseline is already working and should remain the teacher and safety fallback.

First Research Hypothesis

Hypothesis: If the FSM palm trajectory can be converted into OpenVLA-style 7D actions and replayed through the existing G1 reacher, then OpenVLA fine-tuning becomes a meaningful next step.

If this replay fails, then OpenVLA is not yet a good fit for this task without redesigning the action space.

Decision Log

Decision 001 — Do not directly replace the FSM/walker/reacher with OpenVLA

  • Reason: Too many mismatches at once: embodiment, action space, camera distribution, and compute.
  • Expected result: Safer incremental research branch.
  • Rejected alternative: Zero-shot OpenVLA live control.

Decision 002 — Use the FSM as a teacher policy

  • Reason: The FSM already solves the task and exposes phase labels, reach targets, palm pose, grip commands, and object/table metadata.
  • Expected result: Consistent image-action demonstrations without manual teleoperation.

Decision 003 — Build the action adapter before loading OpenVLA

  • Reason: If 7D replay cannot control the G1 stack, fine-tuning OpenVLA is not yet meaningful.
  • Expected result: A local, cheap feasibility test before cloud/model work.

Decision 004 — Use G1-native commands as the first learned action target

  • Decision: Future learned-policy experiments should target walk_cmd, reach_target_pelvis, reach_active, and grip_closed before trying raw 7D palm deltas.
  • Reason: Every-tick teacher-command replay reproduced the teacher trajectory exactly, while hybrid-7D replay still failed.
  • Evidence: Teacher-command replay achieved 0.0 m palm error and ever_attached=True; hybrid-7D had mean palm error 0.229916 m and ever_attached=False.
  • Rejected alternative: Directly feed OpenVLA-style 7D delta actions into the G1 adapter as the first learned control target.
  • Next step: Export a G1-native supervised dataset for future shadow-mode or imitation-learning experiments.

Decision 005 — Export a G1-native supervised dataset before OpenVLA inference

  • Decision: Package the FSM teacher data as image/instruction inputs paired with G1-native command targets.
  • Reason: Step 16 proved the G1-native command interface is replay-faithful, while hybrid-7D replay still failed.
  • Evidence: Step 17 exported 2665 records with an 8D action vector and successful copied-image export.
  • Rejected alternative: Move directly to OpenVLA shadow inference or fine-tuning without auditing the exported dataset.
  • Next step: Audit the dataset and create train/validation splits.

Decision 006 — Treat the current dataset as debugging-only until more data or weighting exists

  • Decision: Do not use the current single-rollout dataset for strong generalization claims.
  • Reason: Step 18 found strong phase imbalance, rare grip transition phases, an idle-heavy run, and a single-trajectory split limitation.
  • Evidence: APPROACH_TARGET=1200 records, but CLOSE_GRIP=2 and OPEN_GRIP=2; audit warnings explicitly mark the split as debugging-only.
  • Rejected alternative: Move directly to OpenVLA shadow inference or fine-tuning using the current dataset as if it were representative.
  • Next step: Build filtered/weighted training views and plan multi-demo collection.

Decision 007 — Preserve the raw dataset and create derived training views

  • Decision: Keep the Step 17 exported dataset unchanged and generate derived full, filtered, and weighted views.
  • Reason: Preserving the raw dataset keeps the evidence trail intact while allowing safer training/debugging manifests.
  • Evidence: Step 19 reduced idle-heavy records from 159 to 10, preserved CLOSE_GRIP=2 and OPEN_GRIP=2, and produced normalized sample weights with mean 1.0.
  • Rejected alternative: Mutate or overwrite the original dataset directly.
  • Next step: Collect multiple demonstrations or add a batch recorder to reduce the single-trajectory limitation.

Decision 008 — Add batch collection before model work

  • Decision: Add a batch recorder and manifest contract before attempting OpenVLA inference or fine-tuning.
  • Reason: Step 18 and Step 19 showed that the dataset was single-trajectory. Batch collection is required before any credible learning experiment.
  • Evidence: Step 20 completed 2/2 no-image teacher demos, each with 2766 records and done_reached=true. The manifest reported num_completed=2, num_failed=0, and total_steps=5532.
  • Rejected alternative: Jump directly into OpenVLA shadow inference or fine-tuning on one rollout.
  • Next step: Combine successful demos from the manifest into a single G1-native dataset.

Decision 009 — Combine batch demos before perturbing scenarios

  • Decision: Add a combined batch dataset exporter before adding scenario randomization.
  • Reason: Step 20 created multiple demo folders, but downstream audit and training-view tools operate on a single dataset artifact. The system needed a clean handoff from batch collection to model-ready data.
  • Evidence: Step 21 combined two successful demos into a 5,330-record dataset, verified row-level provenance, produced a 4,263 / 1,067 train/validation split, and generated 5,022 filtered training-view records.
  • Rejected alternative: Add perturbations immediately while the batch-to-dataset handoff was still manual or undefined.
  • Next step: Add controlled perturbations and record scenario_id / seed metadata so future combined datasets are not deterministic duplicates.

Decision 010 — Separate FSM DONE from true task success before model claims

  • Decision: Treat Step 22 as partially validated and require explicit task-success metrics before using perturbed demos as training-quality evidence.
  • Reason: Perturbation metadata and diversity checks passed, but several perturbed rollouts failed real object transfer and one rollout never reached FSM DONE.
  • Evidence: Step 22 recorded 5 unique scenarios with dx/dy ranges [-0.02, 0.02], yet only 4/5 demos reached DONE, and multiple DONE runs still failed object placement.
  • Rejected alternative: Count recorder completion or FSM DONE alone as task success for perturbed data.
  • Next step: Implement Step 23 robustness gate with task_success, placement checks, final object metrics, and failure_reason.

Decision 011 — Add scripted keyboard as a second teacher source before grasp assurance

  • Decision: Add a scripted keyboard teacher MVP (Step 23A) to automate the original manual-keyboard idea before adding grasp-assurance checks (Step 23B).
  • Reason: The original manual keyboard-control demo was the starting point for this project. Automating it through code creates a deterministic, tunable second teacher source that does not require the FSM state machine.
  • Evidence: Step 23A added vla_bridge/scripted_keyboard.py, a JSON scripted plan, a plan inspector, and a scripted demo recorder. Unit tests passed. The recorder produced demo.jsonl, summary.json, and rendered camera frames. However, visual inspection showed the first open-loop macro did not pick up the cylinder.
  • Rejected alternative: Skip straight to grasp assurance without proving the scripted-keyboard infrastructure first.
  • Next step: Step 23B — add ever_attached, object_lifted, object_on_target_table, task_success, failure_reason, and stop/retry logic before treating scripted demos as training-quality data.

Closing Summary

The practical engineering strategy is to make OpenVLA earn control authority gradually. The FSM remains the baseline. The adapter is the translation layer. The replay test is the gate. Only after that should OpenVLA be placed in shadow mode or fine-tuned.
